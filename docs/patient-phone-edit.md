# Phone editing with registration SMS

The patient profile now has an explicit phone editor. The administrator enters a new owner mobile number and confirms a save-and-send dialog. A normalized unchanged number sends nothing. Because the phone belongs to the owner, every pet linked to that owner shows the updated number; the confirmation UI explains this. Only the selected pet receives this new registration-pattern message.

`editPatientPhone` authenticates through the existing clinic boundary. The service validates UUIDs and Iranian mobile numbers and compares the expected previous phone to reject stale edits. A libSQL write batch atomically creates a unique `sms_deliveries` claim and updates the owner. A per-operation UUID plus payload digest makes replay harmless; only the invocation that created the claim calls the existing registration SMS helper. Provider calls occur after commit, never inside the transaction. No migration, new secret, patient, record or reminder is created.

An API rejection, missing configuration or unknown/timeout result does not revert the saved phone. Accepted responses display the message ID with a delivery caveat. Unknown claims are retained and never automatically retried; a process crash between commit and send can therefore leave an unsent unknown claim requiring manual investigation. This is the same at-most-once tradeoff used by existing SMS workflows, not an exactly-once delivery guarantee. The UI/global mutation locks prevent duplicate clicks, and the database claim protects against concurrent requests and replay across Vercel instances.

Validation: existing integration regressions plus phone validation, stale/missing patient handling, concurrent/replayed requests, formatted unchanged numbers, shared owner updates, acceptance, rejection, timeout, disabled sending, transaction rollback, authorization denial and a DOM test for confirmation/result/error/retry identity. All HTTP in automated tests is mocked; no real SMS is sent during build or CI. Browser/device verification remains pending.
